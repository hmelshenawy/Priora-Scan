# Research: Feature 019 — Control Unit Discovery Foundation

**Date**: 2026-06-15
**Spec**: [spec.md](./spec.md)

## Research Questions

| # | Unknown | Resolution |
|---|---------|------------|
| R1 | How does the existing agent→backend data flow work for vehicle data? | The desktop agent polls `GET /api/v1/obd/agents/:id/live-data/command-queue` every 2s. When a `READ_VEHICLE_DATA` command is received, `queue.py` dispatches to `_vehicle_data_read_handler`, which calls `scan_executor.execute_vehicle_data_read()`. The executor calls `read_vehicle_health(adapter)`, enriches the result dict, and emits a `VEHICLE_DATA_READ` event via `emit_session_event()`. Backend `AgentWebhookController.scanEvents()` routes the event to `handleFeature009Event()`, which calls `VehicleDataService.processVehicleDataRead()`. This service persists the JSONB to `DiagnosticSession.vehicleDataJson`. Feature 019 will follow the same pattern with a new command type `DISCOVER_CONTROL_UNITS` and event type `CONTROL_UNIT_DISCOVERY_READ`. |
| R2 | Where should the discovery module live in the agent? | A new module `desktop-agent/src/obd/commands/control_unit_discovery.py` following the pattern of `vehicle_health.py`. It will import the adapter, define the strategy pattern, and implement `read_control_units(adapter)` which returns the full discovery result dict. The `scan_executor.py` will get a new handler `execute_control_unit_discovery()` that calls this module and emits the event. |
| R3 | Should Feature 019 create a new API endpoint or extend an existing one? | **No new endpoint.** The existing `GET /api/v1/diagnostic-sessions/:sessionId/vehicle-data` already returns the entire `vehicleDataJson` blob. Feature 019 adds a new optional `controlUnitDiscovery` key inside that JSON. The agent triggers discovery via the existing `LiveDataCommand` table with a new `commandType = DISCOVER_CONTROL_UNITS`. The backend routes the event through the existing webhook. |
| R4 | How should the strategy pattern be implemented in Python? | An abstract base class `DiscoveryStrategy` with a method `discover(adapter, request_ids, probe_sequence) -> DiscoveryResult`. The v1 implementation `GenericObdCanDiscoveryStrategy` implements the two-step functional→physical approach. The `read_control_units()` function accepts a strategy parameter defaulting to `GenericObdCanDiscoveryStrategy`. This allows future strategies without modifying the discovery module. |
| R5 | How should negative response codes be mapped? | A module-level dictionary `NEGATIVE_RESPONSE_CODES` in `control_unit_discovery.py` mapping hex strings to human-readable meanings: `11→SERVICE_NOT_SUPPORTED`, `12→SUB_FUNCTION_NOT_SUPPORTED`, `13→INCORRECT_MESSAGE_LENGTH_OR_INVALID_FORMAT`, `22→CONDITIONS_NOT_CORRECT`, `31→REQUEST_OUT_OF_RANGE`, `33→SECURITY_ACCESS_DENIED`, `78→RESPONSE_PENDING`. Unknown codes map to `UNKNOWN_NEGATIVE_RESPONSE`. |
| R6 | How should response parsing work? | `classify_response(raw_response: str, request_id: str) -> ProbeResult` — a pure function that: (1) strips whitespace, (2) checks for `NO DATA` → `NOT_FOUND/NO_RESPONSE`, (3) attempts hex header extraction (first 3 chars if length ≥ 3) → `rawHeader`, (4) attempts negative response detection (`7F` prefix pattern), (5) attempts positive response detection (`6X` prefix pattern), (6) falls back to `UNKNOWN/MALFORMED` for unparseable responses. This function is unit-testable in isolation. |
| R7 | How should confidence be computed? | After all probes complete, a `build_responders()` function iterates the probe results, groups by `responseId`, and computes: if any probe with `method=PHYSICAL` found this `responseId` → `confidence=HIGH`; else if only `method=FUNCTIONAL` → `confidence=LOW`. The `discoveredBy` array is populated by collecting each unique `(method, requestId, probe)` tuple that produced a `DISCOVERED` result for that `responseId`. |
| R8 | How should the frontend display differ between responders and probes? | The default `ControlUnitsPanel` component renders the `responders` array as a table with columns: Response ID, Confidence, Status, Protocol. An optional "Probe Details" collapsible section or tab shows the full `probes` array with Request ID, Probe, Response ID, Method, Status, Response Type, Raw Response. This matches the spec requirement that responders are the default view and probes are the details view. |
| R9 | How does the existing `VehicleDataJson` DTO need to change? | Add `controlUnitDiscovery?: ControlUnitDiscovery` as an optional field. The `isValidVehicleDataJson()` validator must accept sessions without this field (backward compatible) and validate the structure when present. No new database table or migration required. |
| R10 | What command/event types need to be added? | New `LiveDataCommandType`: `DISCOVER_CONTROL_UNITS`. New `ScanEventType`: `CONTROL_UNIT_DISCOVERY_READ`. The agent dispatches on the new command type and emits the new event type. The backend webhook controller routes the new event type. Both are additions to existing enums, not replacements. |

## Key Design Decisions

| Decision | Rationale | Alternatives Considered |
|----------|-----------|------------------------|
| No new API endpoint | Data flows through existing `vehicleDataJson` blob and existing `GET /vehicle-data` endpoint. Minimizes surface area and follows the pattern established by Features 009, 016, 017, 018. | New `/control-units` endpoint — rejected because it creates unnecessary surface area and duplicates the data retrieval path |
| Strategy pattern in agent module | `DiscoveryStrategy` ABC with `GenericObdCanDiscoveryStrategy` concrete implementation. Allows future manufacturer-specific strategies without modifying discovery code. | Hard-coded discovery logic — rejected because it would require rewriting when Feature 020+ adds Toyota, Mercedes strategies |
| `controlUnitDiscovery` as optional key in `vehicleDataJson` | Follows the pattern of `freezeFrame`, `readinessMonitors`, and extended PIDs. No migration needed. | Separate database table — rejected because the spec explicitly prefers JSON storage to keep Feature 019 lightweight |
| Responders-first UI, probes in details view | Reduces noise for technicians (9 probes but potentially 1-2 responders). Matches spec FR-011. | Flat probe table as default — rejected because NOT_FOUND probes create visual noise |
| `discoveredBy` array instead of `requestIds` flat list | Provides full traceability per responder for Feature 020 to build on. Each entry has (method, requestId, probe). | `requestIds: string[]` — rejected because it loses the method and probe context per discovery source |
